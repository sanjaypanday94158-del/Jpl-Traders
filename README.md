# JPL Traders

JPL Traders is a Laravel 12 application rendered with Blade, with Vite-built CSS and JavaScript. The frontend and admin panel run in Laravel; Node.js is only needed to build frontend assets.

## Requirements

- PHP 8.2+ with the extensions required by Laravel and the selected database driver
- Composer 2
- MySQL/MariaDB or another Laravel-supported database
- Node.js and npm for building frontend assets

## Local development

1. Install dependencies and create local configuration/database files:

   ```sh
   composer install
   php -r "file_exists('.env') || copy('.env.example', '.env');"
   php -r "file_exists('database/database.sqlite') || touch('database/database.sqlite');"
   php artisan key:generate
   ```

   The example configuration uses SQLite. If using another database, configure its connection in `.env` instead.

2. Build frontend assets and initialize the database:

   ```sh
   npm ci
   npm run build
   php artisan migrate
   ```

   To access the admin panel locally, create an account with `php artisan admin:create`.

3. Start the development server:

   ```sh
   php artisan serve
   ```

During frontend development, run `npm run dev` in a separate terminal.

## Production deployment

These steps use standard PHP hosting and are not tied to a specific provider. Configure the web server's document root to the project's `public/` directory; do not expose the repository root.

1. Provision PHP 8.2+, Composer, a supported database, and a web server with PHP-FPM or an equivalent PHP handler. Node.js is needed only in the build environment.
2. Create the production database and a private production environment configuration. Set at least:
   - `APP_ENV=production`
   - `APP_DEBUG=false`
   - `APP_URL` to the HTTPS site URL
   - `APP_KEY` to a generated secret (generate it once, keep it private, and preserve it across releases)
   - `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, and `DB_PASSWORD`
   - production mail settings if the app sends email

   For a first deployment using a server-side `.env` file, generate `APP_KEY` once with `php artisan key:generate`; if the host injects environment variables, generate the key securely and set it through the host's secret manager instead.
3. Build each release:

   ```sh
   composer install --no-dev --prefer-dist --optimize-autoloader
   npm ci
   npm run build
   ```

   `public/build/` is generated by Vite and should be included in the deployed release. Do not deploy `node_modules/`.
4. Run the production database migration and create the initial admin account:

   ```sh
   php artisan migrate --force
   php artisan admin:create
   ```

   This prompts for the username and password without putting the password in shell history or application config. The password must be at least 12 characters.

5. Ensure the PHP/web-server user can write to `storage/`, `bootstrap/cache/`, and `public/uploads/images/`. Product images are stored under `public/uploads/images/`; keep that directory on persistent storage and back it up when replacing releases. The `public/uploads/` directory is intentionally excluded from Git.
6. Warm Laravel's caches:

   ```sh
   php artisan optimize:clear
   php artisan optimize
   ```

7. Enable HTTPS and set `SESSION_SECURE_COOKIE=true` for the production environment. Keep `.env`, source files, and `vendor/` outside the web server's document root. Apache can use `public/.htaccess`; configure other web servers to route non-file requests to `public/index.php` (for Nginx, use the standard Laravel `try_files $uri $uri/ /index.php?$query_string` pattern).

For each later release, preserve the production `.env`, `APP_KEY`, database, and uploaded images. Run migrations with `--force`, then refresh Laravel's optimized caches. If a deployment uses Laravel's `public` filesystem disk, create its symlink with `php artisan storage:link`; product uploads use the separate `uploads` disk and are served from `public/uploads/`.

## Validation

```sh
composer validate
php artisan test

```
